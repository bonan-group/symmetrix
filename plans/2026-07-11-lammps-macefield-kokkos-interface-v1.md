# LAMMPS MACEField Kokkos Interface

## Objective

Implement a Kokkos-backed LAMMPS interface for the field-aware MACEField model path. The result should let users run field-coupled JSON models produced by the existing extractor through the LAMMPS Kokkos pair style, with energies, forces, and global virials matching the native MACEField implementation within established tolerances.

Assumptions: "field-ware" means the field-aware MACEField variant already represented by `has_field_coupling` in the JSON extractor and native evaluator. The first LAMMPS interface should support a static uniform electric field vector for the whole simulation, not per-atom fields or field-response output. The primary target is the Kokkos LAMMPS path in `pair_symmetrix`, while the non-Kokkos pair style may reject field-coupled models with a clear error until parity is explicitly requested.

Relevant current state: native MACEField already has field-specific evaluation entry points in `libsymmetrix/source/mace.hpp:36` and field buffers plus response storage in `libsymmetrix/source/mace.hpp:127`. The native forward path inserts field coupling between the H1 product and H1 linear-up stages in `libsymmetrix/source/mace.cpp:88`, `libsymmetrix/source/mace.cpp:95`, and `libsymmetrix/source/mace.cpp:96`, then reverses through the matching field stage in `libsymmetrix/source/mace.cpp:112` and `libsymmetrix/source/mace.cpp:113`. The Kokkos evaluator currently exposes only the ordinary MACE path in `libsymmetrix/source/mace_kokkos.hpp:35` and `libsymmetrix/source/mace_kokkos.cpp:50`, and the LAMMPS Kokkos pair style currently registers only `symmetrix/mace` and `symmetrix/mace/float32` variants in `pair_symmetrix/pair_symmetrix_mace_kokkos.h:21`.

## Verification Criteria

- The Kokkos MACEField JSON loader accepts the existing field-aware JSON generated by `symmetrix/source/symmetrix/extract_mace_data.py:164` and rejects unsupported field couplings with errors that match the native evaluator's constraints.
- Kokkos field-H1 forward and reverse tests match the native/PyTorch-derived expected values at double precision tolerances comparable to `symmetrix/test/test_macefield_native.py:94` and `symmetrix/test/test_macefield_native.py:118`.
- Kokkos full MACEField energy and forces match the native MACEField evaluator for the AlN fixture already used in `symmetrix/test/test_macefield_native.py:122` within the existing native tolerances, with a looser explicitly documented tolerance for float32 if enabled.
- LAMMPS Kokkos runs with a field-coupled JSON produce energies and forces consistent with the Python native evaluator for the same structure and field vector, including finite-difference force checks modeled after `pair_symmetrix/test/test_pair_symmetrix_mace.py:81`.
- The existing non-field LAMMPS pair-style tests continue to pass, confirming that the ordinary `symmetrix/mace` and `symmetrix/mace/float32` behavior was not regressed.
- MPI message-passing mode and no-MPI-message-passing mode either pass field-aware tests on the available LAMMPS build or are explicitly skipped with environment-based reasons rather than silently omitted.

## Potential Risks and Mitigations

1. **H1 indexing in the LAMMPS MPI Kokkos path may be fragile.**
   Mitigation: Add tests that exercise nontrivial atom ordering and ghost exchange, and keep the field transform positioned around the same H1 communication boundary currently used in `pair_symmetrix/pair_symmetrix_mace_kokkos.cpp:715` through `pair_symmetrix/pair_symmetrix_mace_kokkos.cpp:731`.

2. **Electric-field sign and component ordering can drift from MACEField conventions.**
   Mitigation: Reuse the native sign convention from `libsymmetrix/source/mace.cpp:907` through `libsymmetrix/source/mace.cpp:926`, and require forward and reverse field-H1 tests against the existing PyTorch-derived fixtures before enabling LAMMPS tests.

3. **The field-H1 kernel is channel-pair dense and may become a performance hotspot.**
   Mitigation: Start with a clear Kokkos implementation matching the native algorithm, benchmark CPU and GPU timings after correctness, and only then consider optimized team layouts or KokkosBlas variants.

4. **LAMMPS users may expect integration with `fix efield` or per-atom fields.**
   Mitigation: Document the first implementation as a static uniform field supplied to the pair style, reject unsupported per-atom or time-dependent usage explicitly, and leave a clear extension point for future field providers.

5. **Non-Kokkos LAMMPS behavior may be ambiguous for field-coupled JSONs.**
   Mitigation: Either add a targeted non-Kokkos error that explains field-coupled LAMMPS currently requires Kokkos, or implement native LAMMPS field support in a separate follow-up after the Kokkos path is stable.

6. **Float32 field-coupled runs may need looser tolerances than ordinary MACE.**
   Mitigation: Keep double precision as the acceptance target, gate float32 tests separately, and document float32 as performance-oriented once correctness is demonstrated.

## Alternative Approaches

1. Separate `symmetrix/macefield/kk` pair style: This would make field-aware usage explicit and avoid overloading the current settings parser, but it would duplicate most of the pair-style class and make suffix behavior and documentation more complex.
2. Native LAMMPS field support first: This would provide a simpler LAMMPS oracle before Kokkos and could reuse `MACE::compute_node_energies_forces_field`, but it does not address the requested Kokkos interface and may delay GPU-relevant work.
3. Host fallback for the field-H1 transform inside Kokkos: This would be faster to prototype, but it would introduce host-device copies in the hottest path and undermine the purpose of a Kokkos interface.
4. Per-atom electric-field support in the first pass: This matches the native evaluator's broader accepted field shape, but it needs a LAMMPS-side data source and more communication design. A uniform global field is the lower-risk first milestone.
